# TI-99/4A Platform Strategy

## 1. Objective

Use the TI-99/4A as the first physical platform for f128x, an ambitious 128-bit evolution of the TMS9900 architecture. The project replaces the original execution architecture with a new CPU while preserving selected platform hardware and software concepts.

This is not a 128-bit coprocessor attached to an otherwise unchanged TMS9900. Nor does it assume that the new processor can be dropped into the original CPU socket without substantial interface work.

## 2. Architectural relationship

The f128x core takes inspiration from the TMS9900's workspace-oriented architecture but expands it substantially:

- 128 general-purpose registers, each 128 bits wide.
- Native 128-bit scalar integer operations.
- A hardware register file, with a modernized workspace/window mechanism under design.
- Dedicated control state for PC, status, interrupts, and exceptions.
- A new ISA and ABI, not TMS9900 binary compatibility.

The TI-99/4A platform layer will bridge this native architecture to the original machine's devices and legacy address space.

## 3. Platform realities

The TI-99/4A is not a simple CPU connected to a uniform 16-bit motherboard bus:

- The TMS9900 is a 16-bit microprocessor; the console system includes timing/control logic, a 16-bit-to-8-bit data-bus converter, memory decoding, scratchpad RAM, ROM, the TMS9918A video processor, and the TMS9919 sound generator.
- The 44-pin side expansion port exposes address/control/CRU-related signals and an 8-bit bidirectional data interface as documented by the peripheral interface material.
- The CPU-visible memory map includes ROM, cartridge/peripheral regions, memory expansion, and memory-mapped device windows. Video RAM and GROM are accessed through device interfaces rather than behaving as ordinary CPU RAM.
- The TMS9900 uses a workspace model: its sixteen general-purpose registers are memory-resident workspace registers selected through the workspace pointer. The workspace pointer, program counter, and status register form key CPU state.

These details mean a replacement CPU needs a bridge and compatibility subsystem. The electrical, timing, reset, and interrupt requirements must be characterized from primary documentation and hardware measurements.

## 4. Preferred implementation: FPGA motherboard bridge

Build an FPGA board that hosts the f128x CPU and implements a TI-99/4A compatibility subsystem.

Conceptual partition:

1. **f128x core:** 128 × 128-bit GPRs, native 128-bit scalar datapath, and independent ISA control logic.
2. **Native memory subsystem:** f128x address map, RAM controller, and native firmware/runtime memory.
3. **TI compatibility memory map:** mapping of legacy ROM, cartridge, expansion, and device regions into a controlled compatibility address space.
4. **TI peripheral adapters:** timing- and protocol-aware adapters for video, sound, keyboard, joystick, cassette, and selected expansion devices.
5. **Legacy bus bridge:** translate f128x platform transactions into the electrical and timing behavior expected by retained TI devices.
6. **Firmware compatibility layer:** new f128x reset/boot firmware and platform services. Legacy GPL/ROM behavior can be supported through emulation or translation as a separate project.

## 5. Integration phases

### Phase A: Characterize

- Obtain and study the TI-99/4A console technical data and console/peripheral expansion system technical data.
- Record connector pinouts, voltage levels, clocking, bus timing, wait-state behavior, reset, interrupt, and device-select behavior.
- Identify which original chips can be retained directly and which require protocol adapters.
- Decide whether the first prototype is an internal motherboard replacement, a plug-in FPGA board, or a redesigned carrier board.

### Phase B: Standalone f128x FPGA CPU

- Implement and verify the f128x core without TI-specific peripherals.
- Add block RAM, a serial debug console, reset/interrupt support, and a minimal monitor.
- Run ISA tests and a small bare-metal program suite.
- Measure the cost and timing of a 128 × 128-bit register file on candidate FPGA families.

### Phase C: TI peripheral compatibility

- Implement one device adapter at a time, beginning with the simplest observable subsystem.
- Prefer staged bring-up: reset/clock, memory, keyboard/input, video output, sound, then expansion devices.
- Validate electrical compatibility before connecting FPGA I/O to vintage hardware. Use level shifting/buffering where required; never assume FPGA pins tolerate legacy voltage levels.

### Phase D: Software environment

- Define native f128x firmware and ABI.
- Provide an assembler and emulator before attempting a compiler backend.
- Build TI platform libraries for video, sound, keyboard, and storage.
- Evaluate GPL and legacy application compatibility separately. Do not promise TMS9900 binary compatibility from the outset.

## 6. Compatibility levels

| Level | Meaning | Target |
|---|---|---|
| Hardware reuse | Retain selected original TI peripheral chips | Preferred where practical |
| Device compatibility | f128x firmware can use familiar TI devices | Initial platform goal |
| API compatibility | Reimplement selected TI system services | Later goal |
| GPL compatibility | Run selected GPL programs through an interpreter/runtime | Research item |
| TMS9900 binary compatibility | Execute original CPU machine code | Optional emulation/translation, not a first-release requirement |

## 7. Risks and constraints

- Original bus timing and clock phase requirements may constrain the bridge design.
- The TI side port is not a generic modern expansion bus; its data width and signal behavior must be handled explicitly.
- Video and sound chips have their own memory and command protocols.
- Existing firmware assumes TMS9900 reset vectors, workspace behavior, and instruction semantics.
- A 128-bit CPU does not imply that legacy peripherals, memory, or connectors become 128-bit.
- The 128-entry register file is a meaningful FPGA resource and timing consideration; it must be synthesized and measured rather than assumed trivial.
- Board-level work requires schematics, measurements, voltage checks, and a safe test fixture.
