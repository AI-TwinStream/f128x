# TI-99/4A Platform Strategy

## 1. Objective

Use the TI-99/4A as the first physical platform for f128x by replacing the TMS9900 execution core with an FPGA-based f128x CPU. This is a CPU/platform redesign, not a 128-bit coprocessor add-on.

The objective is to preserve as much of the TI-99/4A's recognizable hardware and software environment as practical: video, sound, keyboard, cartridge/expansion ecosystem, and selected firmware or software services.

## 2. Important hardware facts

The TI-99/4A is not a simple 16-bit CPU connected to a uniform 16-bit motherboard bus:

- The TMS9900 is a 16-bit microprocessor with a 16-bit address vector in the console system documentation.
- The console system includes timing/control logic, a 16-bit-to-8-bit data-bus converter, memory decoding, scratchpad RAM, ROM, the TMS9918A video processor, and the TMS9919 sound generator.
- The 44-pin side expansion port exposes address/control/CRU-related signals and an 8-bit bidirectional data interface as documented by the peripheral interface material.
- The CPU-visible memory map includes ROM, cartridge/peripheral regions, memory expansion, and memory-mapped device windows. Video RAM and GROM are accessed through device interfaces rather than behaving as ordinary CPU RAM.
- The TMS9900 uses a workspace model: general-purpose registers are held in memory, with workspace pointer, program counter, and status register forming key CPU state.

These details mean a replacement CPU cannot simply be wired into the original socket and expected to run the old machine unchanged.

## 3. Preferred implementation: FPGA motherboard bridge

Build an FPGA board that hosts the f128x CPU and implements a TI-99/4A compatibility subsystem.

Conceptual partition:

1. **f128x core:** Native 128-bit GPRs and scalar datapath, independent of TI-specific logic.
2. **Memory subsystem:** f128x address translation/map, RAM controller, ROM/cartridge mapping, and device windows.
3. **TI peripheral adapters:** Timing- and protocol-aware adapters for video, sound, keyboard, joystick, cassette, and selected expansion devices.
4. **Legacy bus bridge:** Translate f128x loads/stores and I/O transactions into the electrical and timing behavior expected by the retained TI devices.
5. **Firmware compatibility layer:** New reset/boot firmware and platform services. Legacy GPL/ROM behavior can be supported through emulation or translation as a separate project.

## 4. Integration phases

### Phase A: Characterize

- Obtain and study the TI-99/4A console technical data and console/peripheral expansion system technical data.
- Record connector pinouts, voltage levels, clocking, bus timing, wait-state behavior, reset, interrupt, and device-select behavior.
- Identify which original chips can be retained directly and which require protocol adapters.
- Decide whether the first prototype is an internal motherboard replacement, a plug-in FPGA board, or a redesigned carrier board.

### Phase B: Standalone f128x FPGA CPU

- Implement and verify the f128x core without TI-specific peripherals.
- Add block RAM, a serial debug console, reset/interrupt support, and a minimal monitor.
- Run ISA tests and a small bare-metal program suite.

### Phase C: TI peripheral compatibility

- Implement one device adapter at a time, beginning with the simplest observable subsystem.
- Prefer a staged bring-up: reset/clock, memory, keyboard/input, video output, sound, then expansion devices.
- Validate electrical compatibility before connecting FPGA I/O to vintage hardware. Use level shifting/buffering where required; never assume FPGA pins tolerate legacy voltage levels.

### Phase D: Software environment

- Define a native f128x firmware and ABI.
- Provide an assembler and emulator before attempting a compiler backend.
- Build TI platform libraries for video, sound, keyboard, and storage.
- Evaluate GPL and legacy application compatibility separately. Do not promise TMS9900 binary compatibility from the outset.

## 5. Compatibility levels

| Level | Meaning | Target |
|---|---|---|
| Hardware reuse | Retain selected original TI peripheral chips | Preferred where technically practical |
| Device compatibility | f128x firmware can use familiar TI devices | Initial platform goal |
| API compatibility | Reimplement selected TI system services | Later goal |
| GPL compatibility | Run selected GPL programs through an interpreter/runtime | Research item |
| TMS9900 binary compatibility | Execute original CPU machine code | Not a requirement for the first release |

## 6. Risks and constraints

- Original bus timing and clock phase requirements may constrain the bridge design.
- The TI side port is not a generic modern expansion bus; its data width and signal behavior must be handled explicitly.
- Video and sound chips have their own memory and command protocols.
- Existing firmware assumes TMS9900 reset vectors, workspace behavior, and instruction semantics.
- A 128-bit CPU does not imply that legacy peripherals, memory, or connectors become 128-bit.
- Board-level work requires schematics, measurements, voltage checks, and a safe test fixture.
